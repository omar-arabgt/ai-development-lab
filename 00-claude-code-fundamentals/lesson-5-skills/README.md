# الدرس 5: Skills — كتيّب الإجراءات الجاهزة

## 🗣️ بالعامية

بالشركات المحترمة في "كتيّب إجراءات": كيف منكتب تذكرة، كيف منعمل release، كيف منرد على عميل زعلان. الموظف الشاطر ما بيحفظ كل الكتيّب — **بيعرف وين كل إجراء، وبيفتحه لما يحتاجه**.

الـ Skill هي بالضبط صفحة من هالكتيّب: **إجراء مكتوب مرة وحدة، والـ AI بيفتحه بس لما ييجي شغل من نوعه**. بتقدر تناديها بإيدك (`/linear-ticket`) أو هو بيفتحها لحاله لما يشم إنه الطلب من تخصصها.

### طيب شو الفرق عن CLAUDE.md وعن الـ Subagents؟ (أهم سؤال بالدرس)

| | CLAUDE.md | Skill | Subagent |
|---|---|---|---|
| شو هو؟ | **دستور** المشروع | **إجراء** محدد | **موظف** كامل |
| إيمتى بينقرأ؟ | دايماً، كل جلسة | عند الحاجة بس | عند التفويض |
| مثال | "الكود إنجليزي، production خط أحمر" | "هيك منكتب تذكرة Linear خطوة بخطوة" | "مراجع الكود — قراءة بس" |

قاعدة سريعة: قانون دايم → CLAUDE.md. طريقة عمل شغلة معينة → Skill. شخص إله صلاحيات وذاكرة خاصة → Subagent.

## 🔧 بالتقني

الـ Skill = مجلد باسمها جوا `.claude/skills/`، وفيه ملف `SKILL.md`:

```
.claude/skills/
└── linear-ticket/
    ├── SKILL.md       ← الإجراء نفسه (مع frontmatter)
    └── template.md    ← ملفات مساعدة: قوالب، سكربتات، مراجع
```

```markdown
---
name: linear-ticket
description: Formats a rough bug description into a Linear-ready ticket...
---
# التعليمات التفصيلية هون
```

النقطة الهندسية المهمة — **Progressive Disclosure (الكشف التدريجي):**
- الـ AI بيشوف بس **الاسم والوصف** من كل skill (سطرين خفاف بالذاكرة)
- المحتوى الكامل + الملفات المرفقة **ما بينشحنوا إلا عند الاستدعاء**
- النتيجة: ممكن يكون عندك 50 skill بالمشروع بدون ما تثقل ولا جلسة — مكتبة كاملة، بس الكتاب المفتوح واحد

وهاد حل مشكلة كنا رح نقع فيها: لو حطينا كل الإجراءات بـ CLAUDE.md، الملف بيصير كتاب والـ AI بيتوه. الدستور قصير ودايم، والإجراءات skills عند الطلب.

## 🎯 الـ skill تبع الـ playground: `linear-ticket`

اخترناها **قصداً من مهام الميتنغ الفعلية**: "سجلوا مشاكل المتجر كتذاكر Linear منفصلة، وصف المشكلة بس بدون حلول". هاد إجراء بتكرر عشرات المرات — مثالي يكون skill:

- بتحكيله المشكلة بالعامية كيفما كان
- بيطلعلك تذكرة جاهزة بالإنجليزي: عنوان، وصف، خطوات إعادة، متوقع/فعلي، بيئة (dev/qa/staging/prod)
- وبيطبق سياسة الفريق: **وصف المشكلة بس — ولا كلمة حلول** (القانون مكتوب جوا الـ skill نفسها)

## 🧪 التجربة

افتح جلسة بالـ playground وجرب:

| # | اطلب | شو بتتعلم |
|---|---|---|
| 1 | اكتب `/linear-ticket` وبعدها وصف مشكلة بالعامية، مثلاً: "لما بفتح صفحة السيارة بالعربي، السعر بيطلع بالإنجليزي وشكله مكسور" | الاستدعاء اليدوي — بيطلعلك تذكرة منسقة جاهزة للنسخ |
| 2 | بجلسة جديدة، **بدون** ما تكتب /linear-ticket، احكي: "بدي أسجل مشكلة: صورة السيارة مقصوصة بشاشة الآيفون الصغيرة" | الاستدعاء الأوتوماتيك — بيشم من الوصف إنه هاد شغل الـ skill وبيفتحها لحاله |
| 3 | جرب تطلب منه يقترح **حل** بالتذكرة | بيرفض بأدب — سياسة "problem only" مكتوبة بالإجراء |

## 🏢 كيف تنقلها لمشاريع الشركة

كل إجراء متكرر عندكم = skill مرشحة:
- `/linear-ticket` — نفسها حرفياً (خدها copy-paste من هون!)
- `/release-notes` — من git log لملاحظات إصدار بالصيغة تبعتكم
- `/flutter-widget` — how-to إنشاء widget بهيكلة مشروعكم (folders, state management, naming)
- `/translation-check` — إجراء فحص ملفات الـ l10n قبل أي release

والجملة للميتنغ: **"حولنا كتيّب إجراءات الفريق لأوامر — المعرفة اللي كانت بروس الناس صارت أصول بالريبو"** (تذكر مصطلح tacit → explicit knowledge من الدرس 1؟ هاد هو، على مستوى الفريق كله).
