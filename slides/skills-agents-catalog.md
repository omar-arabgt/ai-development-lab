## أولاً: الـ Skills / Commands — `.cursor/commands/`

بتنادى بـ `/` من اللوحة أو الـ IDE. كل وحدة ملف markdown فيه: الخطوات + السياسات المخبوزة + حدود التوقف.

### `/sentry-sweep` — الكنّاس
**وظيفته:** يسحب أعلى الأخطاء غير المحلولة من Sentry ويحولها بطاقات Linear.
**شو جوّاته:**
- الوجهة الثابتة: org `arabgt`، مشروع `mobile-prod` (بالموبايل) / `backend-prod` (بالباكند)
- **Dedupe أولاً**: البطاقة موجودة؟ تعليق تحديث، ممنوع نسخة ثانية
- بطاقة = مشكلة فقط، ممنوع اقتراح حلول (سياسة الفريق) + ليبل `Sentry`
- كل بطاقة بتنتهي بقسم **"Sentry close-out"**: الرقم والرابط + "الـ resolve يدوي بشري بعد التحقق"
- **Sentry قراءة فقط — دايماً** • المشروع الوجهة مش موجود؟ **وقّف وقول** — ممنوع بديل

### `/linear-ticket` — كاتب التذاكر
**وظيفته:** يحول وصف مشكلة بأي لغة لتذكرة Linear منسقة وينشئها فعلياً.
**شو جوّاته:**
- القالب: عنوان `[Area] المشكلة` + وصف + خطوات إعادة إنتاج مرقمة من فتح التطبيق + Expected/Actual + البيئة
- التذكرة بالإنجليزي مهما كانت لغة المدخل
- الوجهة ثابتة: team ArabGT / project "ArabGT Mobile App" — **ما بيسأل وما بيغير**
- البيئة/المنصة غامضة؟ **سؤال واحد** قبل الإنشاء — ممنوع التخمين
- **مشكلة فقط، ممنوع الحلول** — بيرفض بأدب لو انطلب منه حل

### `/daily-report` — تقرير الصباح
**وظيفته:** "شو انكسر مبارح ومين عارف عنه؟"
**شو جوّاته:**
- من Sentry: الجديد بآخر 24 ساعة + الراجع (regressions) + الأكثر تكراراً
- الترتيب: crashes أولاً، بعدين حسب المستخدمين المتأثرين
- مقارنة مع Linear: مين إله بطاقة (برابطها) ومين متروك
- المخرج: عناوين رقمية + جدول + فقرة نمط ملحوظ — بصفحة وحدة
- عينة أقل من ~10 أحداث = "إشارة أولية مش استنتاج" • **قراءة فقط** — بده يفتح تذاكر؟ بيحيلك على `/sentry-sweep`

### `/release-check` — بوابة الإصدار
**وظيفته:** حكم GO / NO-GO قبل أي ترقية.
**شو جوّاته (موبايل):** analyze صفر أخطاء + كل التستات خضرا + الشغل على برانش من dev + **فحص الـ diff**: ممنوع يلمس `environments/prod/` أو ملفات التواقيع — أي لمسة = NO-GO تلقائي
**شو جوّاته (باكند):** manage.py check + كل التستات محلياً + سلامة الـ migrations (جديدة مسموح، تعديل ملجونة ممنوع) + ممنوع يلمس `.env*` + فحص حدود api/web
**المشترك:** ممنوع يبني أو يرفع أو ينشر أي شي • **NO-GO لازم يعدد الأدلة — وممنوع يتلطف**

### `/parallel-tasks` — قانون التوزيع
**وظيفته:** توزيع مهام على agents متوازيين بدون كوارث.
**شو جوّاته:**
- خريطة الملفات **قبل** الإطلاق — **ممنوع ملف واحد عند اثنين**؛ التداخل = agent واحد بالتسلسل
- worktree + برانش لكل agent (`fix/<ticket>-<slug>`) — ممنوع الشغل بالمجلد الرئيسي
- كل agent: كل التستات خضرا قبل الـ PR • مهمة = PR واحد • بالنهاية تقرير + تنظيف الـ worktrees

## ثانياً: الـ Subagents — `.cursor/agents/`

شخصيات معرفة بملفات: دور ضيق + معايير مكتوبة + صلاحيات على قد الدور.

### ريبو الموبايل (3)

| الـ Agent | دوره | شو بتعريفه | صلاحياته |
|---|---|---|---|
| **flutter-reviewer** | مراجعة كود Flutter بقوانيننا | التنقل حصراً ArabgtGo (مش Get.toNamed) • تشريح الـ feature القياسي • ممنوع تقليد مجلدات الاستثناء الـ 7 • RTL (التطبيق عربي/إنجليزي) • أنماط GetX (bindings → controllers → data source) • قسم أداء (rebuilds، const، صور) | **قراءة فقط** |
| **qa-engineer** | كتابة الفحوصات | لكل feature/fix تست بيثبته • التست بيفشل أول وبعدين الحل بينجحه • unit + widget + integration حسب الحالة | **مجلدات التست بس** |
| **pr-reviewer** | الحكم النهائي عالـ PR | بيقرأ الـ diff مقابل الهدف • بيفحص ضد الـ rules • بيتأكد في تست • حكم صريح **READY / NOT READY** + اقتراح عنوان ووصف للـ PR • بيقارن عدة PRs ويطلع ترتيب دمج | **قراءة فقط** |

### ريبو الباكند (5)

| الـ Agent | دوره | شو بتعريفه | صلاحياته |
|---|---|---|---|
| **django-reviewer** | مراجعة كود Django | حدود الـ endpoints (موبايل→api/، ويب→web/، غامض→اسأل) • جداول الأخبار read-only mirrors (ReadOnlyRouter — خط أحمر) • modeltranslation (ar/en) • انضباط الـ migrations • أسلوب match-the-file | **قراءة فقط** |
| **api-qa** | فحوصات الـ API | manage.py test محلياً فقط • تغطية الـ endpoints الجديدة • **assertNumQueries** كحارس N+1 بالتستات | **مجلدات التست بس** |
| **web-reviewer** | مراجعة الويب (Django templates) | القوالب بـ templates/ وفصل web/webv2 • حارس XSS: أي `|safe` أو `mark_safe` = blocker • إعادة استعمال templatetags • RTL • أساسيات SEO | **قراءة فقط** |
| **performance-reviewer** | صيّاد البطء | تتبع سلاسل الـ queries وكشف N+1 (select_related/prefetch_related) • الـ pagination عبر `api/pagination.py` • الكاش عبر `api/cache_utils.py` • الفهارس • كلفة الـ cross-db على mysql_db | **قراءة فقط** |
| **pr-reviewer** | الحكم النهائي | نفس نسخة الموبايل بس بقوانين الباكند | **قراءة فقط** |

## ثالثاً: الـ CI Agents — `.github/workflows/` (نفس العقول، بس بتصحى لحالها)

| الـ Workflow | زناده | شو بيعمل بالمختصر |
|---|---|---|
| **ai-pr-review** | كل PR (فتح/تحديث) | بيشغل pr-reviewer عبر Cursor CLI: تعليق مراجعة + `VERDICT` — NOT READY بيفشّل الـ check (وبيرفق برومبت إصلاح جاهز للصق بـ Cursor) • التحديثات بتتراجع **تزايدياً** (بس الجديد) |
| **promotion-gate** | PR على production | production بيقبل **بس من staging** — غيره ❌ فوراً |
| **sentry-sweep** | يومياً 7:00 صباحاً + زر يدوي | بينفذ سياسة `/sentry-sweep` نفسها بالـ API (بلا MCP) |
| **bug-fix** | إشارة من الـ relay أو زر يدوي برقم الخطأ | السلسلة الكاملة: Sentry → تذكرة → In Progress → برانش → تست فاشل → حل → PR → comment بالتفاصيل → "In Review from AI" *(صيغة الـ staging/qa النهائية بانتظار قراري القسم 14)* |
