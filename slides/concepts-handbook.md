# 1. التعريفات العامة (Project Memory & Permissions)

## Project Memory — ذاكرة المشروع

**شو هي:** ملف بيعرّف الـ AI على مشروعك من أول ثانية: الـ structure، الـ architecture، طريقة كتابة الكود (naming, patterns, error handling)، والممنوعات. بدونه كل جلسة بتبلش من الصفر وبتخترع أعراف من راسها. وأهم صفة فيه: **بيعيش جوا الـ repo** — يعني أي حدا يعمل clone بتيجي المعرفة معه. أصول تبعت الفريق، مش إعدادات على جهاز حدا.

**عنا على Claude:** ملف `CLAUDE.md` بجذر الـ repo. بينقرأ **أوتوماتيكياً** بكل جلسة. منخلي الـ AI نفسه يدرس الكود ويكتب المسودة، وإحنا منراجع.

**وعلى Cursor:** مجلد `.cursor/rules/` بجذر الـ repo — ملفات `.mdc`، وبتقدر تعمل أكثر من ملف (واحد عام + واحد لكل جزء من المشروع مع `globs` بتحدد أي ملفات بيخصها). بتنقرأ أوتوماتيكياً كمان. عملياً: منكتب القوانين مرة ومنعكسها بالملفين — **مصدر حقيقة واحد، ملفين**.

## Permissions & File Scopes — الصلاحيات وحدود التعديل

**شو هي:** قوائم صريحة: شو الـ AI مسموحله ينفذ بدون سؤال (allow)، شو بده إذنك (ask)، شو ممنوع نهائياً (deny) — وأي ملفات إله حق يعدلها. مش أدب واتفاق — النظام بيفرضها.

**عنا على Claude:** `.claude/settings.json` بجذر الـ repo → قسم `permissions` بقوائم allow/ask/deny بمستوى الأمر الواحد (مثلاً: `Bash(flutter test *)` مسموح، `Bash(rm -rf *)` ممنوع) وبمستوى الملفات. **بينلجن مع الـ repo** فبيوصل للفريق كله.

**وعلى Cursor:** إعدادات الـ Agent (auto-run allowlist/denylist للأوامر) — بس انتبه: **بتنحفظ بإعدادات التطبيق على الجهاز، مش بالـ repo** — يعني كل واحد بالفريق لازم يضبطها عنده. هاي نقطة فرق عملية: تبعت Claude بتنتشر مع الـ clone، تبعت Cursor لأ.

# 2. Skills — الإجراءات الجاهزة

**شو هي:** إجراءات الفريق مكتوبة **مرة وحدة** بملف، والـ AI بيفتحها **بس لما ييجي شغل من نوعها** (progressive disclosure — بيشوف العنوان دايماً والمحتوى عند الحاجة، فما بتثقل الجلسات). والأهم: **السياسات مخبوزة جواها** — سياسة "التذكرة توصف المشكلة بلا حلول"؟ مكتوبة جوا الـ skill، والـ AI نفسه بيرفض يخالفها. بتنادى يدوياً (`/linear-ticket`) أو بتنشط لحالها من وصف طلبك.

**عنا على Claude:** مجلد `.claude/skills/<اسم>/SKILL.md` بالـ repo (+ ملفات مرفقة متل `template.md`). أمثلة بنيناها: `/linear-ticket` (تذكرة من وصف بالعامية، problem-only)، `/parallel-tasks` (توزيع مهام متوازية بسياسة "ولا agent-ين على ملف").

**وعلى Cursor:** موجودة بنفس الشكل تقريباً — **SKILL.md files** (من إصدار 2.4) بتعطي الـ agents إجراءات ومعرفة متخصصة، وفي كمان **Commands** (أوامر `/` مخصصة بمجلد `.cursor/commands`). يعني نفس skill التذاكر منقدر نوفرها للأداتين — المحتوى نفسه، مكانين.

# 3. Hooks & Production Safety — الحراس وخط الإنتاج الأحمر

## Hooks — الحراس

**شو هي:** كود صغير بيشتغل **أوتوماتيكياً عند حدث معين** — وأهم استخدام: يفحص العملية **قبل تنفيذها** ويقدر **يمنعها**. الفرق الجوهري عن أي "تعليمات": التعليمات الـ AI بيلتزم فيها بأدب وممكن نظرياً يغلط — الـ hook **النظام نفسه بينفذه**، ما في مجال أدب. (عنا الحارس طخّ مؤلفه وهو بيبنيه — ما بيجامل حدا 😄)

**عنا على Claude:** قسم `hooks` بـ `.claude/settings.json` — حدث `PreToolUse` بيمرر تفاصيل العملية لسكربت bash عبر stdin، والسكربت بيرجع **exit 2 للمنع** برسالة سبب. ناضجة وقديمة (GA) ومجربة عنا فعلياً بثلاث حراس شغالين.

**وعلى Cursor:** صارت موجودة (من أواخر 2025): ملف `.cursor/hooks.json` بجذر الـ repo (أو `~/.cursor/hooks.json` عام) — أحداث بنفس الأسلوب، أهمها `beforeShellExecution` اللي بتفحص الأمر قبل ما يركض وبتقدر تمنعه. **أحدث عهداً** من تبعت Claude (شهور مقابل سنين) — منستعملها عند مستخدمي Cursor كطبقة ثانية، بس حراس الأتمتة الرسميين عنا على Claude.

## Production Safety — الخط الأحمر

**شو هو:** مبدأ إنه الـ AI **ما بيوصل للإنتاج أبداً** — مش كوعد، كبنية بطبقات: (1) الحراس بيمنعوا أي أمر فيه أسماء prod (DBs، بيئات، مساحات الشركة بـ Sentry/Linear)؛ (2) permissions ما بتسمح بأدوات النشر؛ (3) الحسابات نفسها معزولة — credentials الإنتاج مش على أجهزة التطوير أصلاً؛ (4) كل شي بيمر عبر PR ببوابات ودمج بشري. **وبحالة ArabGT مع Django backend هاد أهم قسم**: منع `manage.py migrate/shell` على أي بيئة إنتاج، ومنع أي أمر فيه أسماء الـ prod DBs الفعلية.

**عنا على Claude:** hooks بأنماط الإنتاج الحقيقية (بتتحدد بالمرحلة 0 من خطة النقل) + عزل الحسابات + least privilege بالـ `--allowedTools` لكل أنبوب.

**وعلى Cursor:** نفس الأنماط منحطها بـ `.cursor/hooks.json` (beforeShellExecution) لطبقة موازية عند مستخدميه — والعزل والحسابات نفس الشي للاثنين.

# 4. Multi-Agent Development — الفريق المتوازي

## Git Worktrees — النسخ المعزولة

**شو هي:** ميزة بـ **git نفسه** (مش بأي أداة AI): نسخة ثانية كاملة من الـ repo بمجلد منفصل وعلى branch منفصل — **بدون clone جديد**. كل agent بياخد نسخته = مستحيل يلمسوا ملفات بعض. ومجلدك الرئيسي والـ editor المفتوح ما بينلمسوا. أمر واحد: `git worktree add ../wt/task-a -b task/a` — **by default، ولا سطر كود منكتبه**.

**عنا على Claude:** جلسات Claude بتشتغل بالـ worktrees مباشرة، والـ orchestrator بيديرهم.

**وعلى Cursor:** **صار أصلي بالكامل** من Cursor 2.0: الـ parallel agents بيشتغلوا بـ worktrees معزولة تلقائياً — لحد **8 agents بنفس الوقت** — وفي `/multitask` بيقسم طلبك على subagents لحالهم، وworktree.json لتفعيل "Build in Parallel". يعني التوازي متاح للأداتين — مستخدم Cursor من الواجهة، ومستخدم Claude من الجلسة.

## Orchestrator — المايسترو

**شو هو:** بدل ما تدير التوازي بإيدك (تفتح نسخ، توزع، تدمج)، **جلسة وحدة بتاخد الطلب كامل**: بتجهز الـ worktrees، بتطلق agent لكل مهمة بالتوازي، بتستنى الكل، بتدمج الـ branches، بتنظف، وبتسلمك النتيجة. انت بتحكي المهام **مرة وحدة**.

**عنا على Claude:** جلسة بتفعّل skill الـ `/parallel-tasks` — وفيها **السياسة الذهبية مخبوزة**: قبل أي توازي بتفحص تقاطع الملفات؛ مهمتين على نفس الملف = **بترفض التوازي** وبتعرض التسلسل. (هاي السياسة هي اللي بتخلي الدمج بصفر conflicts بالتصميم مش بالحظ.)

**وعلى Cursor:** الـ `/multitask` والـ subagents (من 2.4) بيعملوا التقسيم والتوزيع — والقاعدة تبعت "ولا مهمتين على ملف" منحطها بالـ rules عشان تنطبق هناك كمان.

## Subagents — الموظفين المتخصصين

**شو هم:** agents فرعيين بتعريف وصلاحيات محددة — كل واحد بـ context خاص (شغله الداخلي ما بيلوث ذاكرة الجلسة الرئيسية) وبأدوات محددة (مراجع كود بدون صلاحية تعديل = **مستحيل** يعدل، مش "ما بيصير").

**عنا على Claude:** ملفات `.claude/agents/<اسم>.md` — تعريف + أدوات مسموحة + شخصية. أمثلة بنيناها: code-reviewer وsecurity-auditor (قراءة بس).

**وعلى Cursor:** subagents موجودين من 2.4 — كل واحد بـ context window مستقل، بينطلقوا بالتوازي لمهام فرعية.

# 5. MCP — الموصل الموحد (Sentry, Linear, PostHog)

**شو هو:** بروتوكول موحد بيوصل الـ AI بالخدمات الخارجية — متل **USB-C**: منفذ واحد، أي جهاز. الخدمة بتعمل MCP server بيعرض أدواتها (جيب issues، أنشئ ticket...)، وأي AI بيحكي البروتوكول بيستعملها متل أدواته العادية. **والأهم للقرار: Claude وCursor بيحكوه الاثنين** — يعني أي ربط منبنيه استثمار واحد بيخدم الأداتين.

**عنا على Claude:** `claude mcp add -s user --transport http sentry https://mcp.sentry.dev/mcp` (ونفسها لـ Linear وPostHog) + مصادقة OAuth. وللفريق: ملف `.mcp.json` بجذر الـ repo بيعرّف السيرفرات للكل — كل واحد بيصادق بحسابه.

**وعلى Cursor:** ملف `.cursor/mcp.json` (بالمشروع) أو `~/.cursor/mcp.json` (عام) — نفس السيرفرات بالضبط، نفس الصيغة تقريباً.

**شو منعمل فيه:** من **Sentry** — قراية الـ crash والـ stack trace، تشخيص، إصلاح، وresolve. من **Linear** — تذكرة من وصف بالعامية، فرز التذاكر الجديدة (أولوية/تصنيف/ربط مكررات حتى عبر اللغتين)، وticket→spec→PR. من **PostHog** — حوار مع بيانات الاستخدام وتقارير.

# 6. Testing — الفحص بثلاث مراحل

## Integration Tests — الرحلة ككود

**شو هي:** رحلة المستخدم مكتوبة كفحص: يفتح التطبيق، يكبس سيارة، يشوف التفاصيل، يحجز، يتأكد من التأكيد — كل خطوة assertion بتنجح أو بتفشل. حتمية 100%، **صفر AI بالتشغيل** — الـ AI بيكتبها مرة من وصفك بالعامية (الجزء الغالي)، وبعدين بتركض ببلاش للأبد. للموبايل: `integration_test/` جوا مشروع Flutter. للباك إند: pytest على Django (والفحوصات العادية هناك معزولة أصلاً بـ test DB مؤقتة).

## GitHub Actions — المشغّل والبواب

**شو هو:** منصة CI تبعت GitHub: ملف YAML بـ `.github/workflows/` بيوصف "عند حدث كذا شغّل خطوات كذا". عنا ثلاث استعمالات: **بوابة كل PR** (فحوصات + مراجعة AI + قفل دمج بـ Branch Protection)، **الليلي** (الرحلات على iOS وAndroid بتقارير نجح/فشل لكل منصة)، **والأسبوعي** (المسح الشامل + إرسال لـ Test Lab). مجاني للريبو العام، ودقايق مشمولة للخاص.

**مراجعة الـ PR بالـ AI:** عنا claude-code-review action رسمية — البرومبت بإيدنا (منخصصه: Flutter، RTL، أنماط Django). بديل Cursor: **Bugbot** (خدمة مستضافة — أقل تحكم) أو action مجتمعية حوالين cursor-agent CLI.

## Firebase Test Lab — الأجهزة الحقيقية

**شو هو:** معرض موبايلات فيزيائية عند Google — بتبعتله تطبيقك **ونفس فحوصات الرحلة**، بيركضها على Pixel وSamsung حقيقيين، وبيرجع تقرير + **فيديو لكل جهاز**. أسبوعياً، وضمن حصة مجانية يومية (10 افتراضي + 5 فيزيائي). بيمسك اللي الـ emulator أعمى عنه: تخصيصات الشركات للنظام، معالجات ضعيفة، شاشات غريبة.

# 7. Headless & Automation — الأتمتة والسيرفر

## Headless Mode — التشغيل بلا واجهة

**شو هو:** بدل الجلسة التفاعلية، أمر واحد بينفذ مهمة كاملة وبيطلع — قابل للاستدعاء من سكربت أو cron أو webhook. **هاد حجر أساس كل الأتمتة.**

**عنا على Claude:** `claude -p "المهمة..." --allowedTools "..."` — مع قاعدة القوائم المشدودة: بالضبط قد المهمة، لا أكثر (أمان) ولا أقل (الأنبوب بينشل بصمت).

**وعلى Cursor:** صار موجود — **cursor-agent CLI** بوضع `-p`، وبيشتغل بـ CI. قرارنا نبني الأتمتة على Claude لأسباب اقتصادية ونضج (تحت) مش لأنه Cursor ما بيقدر.

## الزنادات: Webhooks & Cron

**Webhook (الجرس):** بتعطي الخدمة عنوان وبتقلها "لما يصير شي دقيلي" — Sentry عند crash، Linear عند ticket، GitHub عند PR. المستمع عنا: سكربت ~70 سطر على السيرفر بيطلق الأنبوب عند كل دقة.
**Cron (المنبّه):** "كل يوم الساعة 7:00" — للتقرير الصباحي والفحوصات الدورية. والقاعدة المقدسة بالاثنين: **كل شي صريح ومحدد مسبقاً — ولا سؤال تفاعلي بنص أنبوب** (سؤال بلا إنسان = تجمد صامت).

## سيرفر الأتمتة (AWS)

**التوزيعة:** أجهزة المطورين للتفاعلي (وكل شي محلي لحد الـ PR) ← GitHub Actions للبوابات والمجدول المرتبط بالريبو ← **EC2 صغير دايم الصحو** (t4g.small بيكفي) للـ webhooks والجدولة والأنابيب وتوصيل Slack. ليش سيرفر؟ **اللابتوبات بتنام وهاد ما بينام.** والشغل الثقيل عند مزود الـ AI عبر API — السيرفر بس بيسمع ويجدول ويوزع.

## ليش الأتمتة على Claude؟ (الأسباب المحدثة بعد التدقيق)

مش "لأنه Cursor ما بيقدر" — بـ 2026 الاثنين بيقدروا. الأسباب: (1) **~5.5x توكنز أقل لنفس المهمة** بمقارنات مستقلة؛ (2) **فوترة API شفافة لكل أنبوب** (batch −50% + caching) مقابل نظام credits؛ (3) تكامل GitHub **رسمي من الشركة الأم**؛ (4) حراس أقدم وأنضج؛ (5) **الـ playbook تبعنا كله مبني ومجرب عليه**. وCursor بيظل ملك المحرر.

# 8. Database Copies — نسخ الداتابيس للـ agents

**شو هي:** نفس فلسفة الـ worktrees بس على الداتا: **نسخة DB معزولة لكل مهمة**. ليلياً snapshot من dev بيصير قالب محلي (مع تعقيم لو فيه داتا حقيقية)؛ عند كل مهمة سكربت بيولد نسخة بثواني (`createdb task_x -T tpl_dev`) وبيكتب `DATABASE_URL` بـ `.env` جوا الـ worktree — فكل agent على قاعدته تلقائياً. بأنبوب Sentry الأوتوماتيكي: spawn بأول السكربت + `trap despawn EXIT` (بترمي النسخة حتى عند الفشل). **الـ dev المشتركة ولا مرة بتنلمس** — وحارس بيمنع أي أمر باتجاه القواعد المشتركة حتى لو الـ AI نسي. (وفحوصات Django العادية معزولة أصلاً — pytest بيعمل test DB لحاله؛ النسخ لإعادة إنتاج bugs بداتا واقعية.)

**على الأداتين:** الآلية git + Postgres + env — محايدة تماماً، بتخدم Claude وCursor بنفس الشكل.

# 9. الحلقة الكاملة — Sentry Error ← Linear Ticket ← GitHub PR

crash الساعة 3 الفجر ← Sentry alert rule بتدق webhook للسيرفر ← المستمع بيطلق أنبوب واحد: بيسحب الـ issue، **بينشئ Linear ticket** (وصف + رابط + أولوية)، بيولد نسخة DB، بيعيد إنتاج الـ bug، بيصلّح على branch، بيفحص، بيفتح **PR** موصوف، بيعلق عالـ ticket وبينقلها In Review ← بوابات الـ PR بتشتغل لحالها ← **الصبح: المهندس بيقرأ الـ diff وبيكبس Merge** — الإيد البشرية الوحيدة ← webhook الدمج بيسكّر الحلقة: ticket → Done وissue → Resolved.

**كل مقاطع السلسلة مجربة فعلياً** — والوصل النهائي بالـ webhooks هو شغل مرحلة السيرفر بخطة النقل.

# الخلاصة الذهبية — وين كل شي بيعيش

| الفئة | أمثلة |
|---|---|
| **بالـ repo** (بينتشر مع الـ clone) | CLAUDE.md، .cursor/rules، permissions، hooks، skills، workflows، الفحوصات، سكربتات الـ DB |
| **عالجهاز/الحساب** (مرة لكل واحد) | ربط MCP ومصادقاته، حراس مساحات الشركة، إعدادات Cursor للـ auto-run |
| **عالسحابة** (مرة للفريق) | GitHub Secrets، Branch Protection، Firebase، سيرفر AWS |
| **by default ببلاش** | git worktrees، الاسترجاع (restore/revert)، التوازي نفسه، عزل test DBs بـ Django |
